## 効果的なプロンプトの構成要素

### 1. 検証手段を含める（最重要）

Claudeが自身の作業を確認できる手段を必ず含める。

| 戦略 | Before | After |
|------|--------|-------|
| 検証基準の提供 | 「メールバリデーション関数を実装して」 | 「validateEmail関数を書いて。user@example.comはtrue、invalidはfalse、user@.comはfalse。実装後にテストを実行して」 |
| UI変更の視覚確認 | 「ダッシュボードを改善して」 | 「[スクリーンショット貼付] このデザインを実装して。結果のスクリーンショットを撮って元と比較し、差分をリストアップして修正して」 |
| 根本原因の解決 | 「ビルドが失敗する」 | 「このエラーでビルドが失敗する: [エラー貼付]。修正してビルドが成功することを確認して。エラーを抑制せず根本原因を解決して」 |

### 2. スコープを明確にする

| 戦略 | Before | After |
|------|--------|-------|
| タスクのスコープ | 「foo.pyのテストを追加して」 | 「foo.pyのユーザーがログアウトしたエッジケースのテストを書いて。モックは避けて」 |
| 既存パターンの参照 | 「カレンダーウィジェットを追加して」 | 「ホームページの既存ウィジェットの実装を確認して。HotDogWidget.phpが良い例。このパターンに従って新しいカレンダーウィジェットを実装して」 |
| 症状の詳細記述 | 「ログインバグを修正して」 | 「セッションタイムアウト後にログインが失敗する。src/auth/のauth flowを確認して。再現するテストを書いてから修正して」 |

### 3. リッチコンテンツの活用

- `@` でファイルを直接参照する
- スクリーンショット・画像をペーストする
- ドキュメントのURLを提供する（`/permissions` で許可ドメイン設定）
- `cat error.log | claude` でデータをパイプする
- Claudeに自分でコンテキストを取得させる

### 4. 曖昧なプロンプトの使いどころ

探索的な目的で意図的に曖昧にする場合は有効：
- 「このファイルで何を改善できる？」
- 「このアーキテクチャの問題点は？」

## 4フェーズワークフロー

大きなタスクは以下の4フェーズで進める：

1. **Explore** - Plan Modeでコードを読み、理解する。`@` でファイルを参照し、アーキテクチャを把握する
2. **Plan** - 詳細な実装計画を作成する。影響範囲、エッジケース、テスト戦略を明記する
3. **Implement** - Normal Modeで実装し、計画に照らして検証する。各ステップ後にテストを実行する
4. **Commit** - 説明的なメッセージでコミット・PR作成。変更の「なぜ」を記述する

**ポイント**: ExploreとPlanはPlan Modeで行い、Implementで初めてコード変更する。計画なしの実装はアンチパターン。

## インタビューパターン

大きな機能開発では、Claudeにインタビューさせる：

```
[簡潔な説明]を構築したい。AskUserQuestionツールで詳細にインタビューして。

技術的実装、UI/UX、エッジケース、懸念事項、トレードオフについて聞いて。
明白な質問は避け、私が考えていないかもしれない難しい部分を掘り下げて。

すべてカバーしたらSPEC.mdに仕様書を書いて。
```

仕様書完成後、新しいセッションで実装を開始する（クリーンなコンテキストで集中）。
