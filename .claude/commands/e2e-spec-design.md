# /e2e-spec-design - E2Eテスト仕様書作成コマンド

画面仕様書（Markdown/Excel）からE2Eテスト仕様書を生成する。生成したテスト仕様書は `/e2e-spec-impl` でPlaywrightテストコードに変換可能。

---

## [1/6] 入力ファイル解析

### 仕様書パスの取得

```
仕様書パス: $1
```

$1が空の場合、ユーザーに質問：

「テスト仕様書を作成する画面仕様書のパスを入力してください。
対応形式: Markdown (.md), Excel (.xlsx)
例: docs/specs/auth/login.md」

### 仕様書の読み込み

Readツールで仕様書を読み込み、以下を特定：

1. **画面情報**: 画面ID、画面名、URL、認証要否
2. **画面要素**: フォーム要素、表示要素、ナビゲーション要素
3. **機能一覧**: 主要機能、副次機能

### 対象画面の確認

複数画面が含まれる場合、AskUserQuestionで対象画面を確認：

```javascript
AskUserQuestion({
  questions: [{
    question: "テスト仕様書を作成する画面を選択してください。",
    header: "対象画面",
    options: [
      { label: "[画面名1]", description: "[概要]" },
      { label: "[画面名2]", description: "[概要]" },
      { label: "すべて", description: "検出したすべての画面" }
    ],
    multiSelect: true
  }]
})
```

## [2/6] 既存テスト分析

### 目的

重複テストの作成を防止し、既存テストとの整合性を確保する。

### 既存テスト仕様書の検索

Globツールで既存の仕様書を検索：

```javascript
Glob({ pattern: "tests/e2e/specs/**/*.spec.md" })
```

対象画面に関連する既存仕様書を特定し、テストケースの重複をチェック。

### 既存テストコードの検索

Globツールで既存のテストコードを検索：

```javascript
Glob({ pattern: "tests/e2e/tests/**/*.spec.ts" })
```

対象画面に関連するテストファイルが既に存在するか確認。

### 重複・関連テストの検出

以下の項目を確認：

| チェック項目 | 確認内容 |
|-------------|---------|
| **完全重複** | 同一画面・同一機能のテスト仕様書が既に存在しないか |
| **部分重複** | 類似テストケース（同じ操作手順）が既に存在しないか |
| **関連テスト** | 依存関係のあるテスト（ログイン→ダッシュボード等）が存在するか |

### 既存テスト分析結果の報告

```javascript
AskUserQuestion({
  questions: [{
    question: "既存テスト分析が完了しました：\n\n【検出結果】\n- 既存仕様書: {件数}件検出（{ファイル名リスト}）\n- 既存テストコード: {件数}件検出\n- 重複の可能性: {あり/なし}\n\n{重複がある場合の詳細}\n\nこのまま新規仕様書の作成を続行しますか？",
    header: "既存テスト分析",
    options: [
      { label: "続行 (Recommended)", description: "新規仕様書の作成を続行" },
      { label: "既存テストを確認", description: "検出した既存テストを表示して確認" },
      { label: "キャンセル", description: "コマンドを終了" }
    ],
    multiSelect: false
  }]
})
```

**「既存テストを確認」選択時**:
検出した既存仕様書・テストコードの内容をユーザーに表示し、再度続行/キャンセルを確認。

## [3/6] テストケース設計

### スキル参照

**playwright-guidelines** の詳細ガイドラインを参照：

```javascript
Skill('playwright-guidelines')
```

参照セクション:
- SKILL.md 83-108行: テスト仕様書フォーマット
- references/pom-patterns.md: Page Objectパターン
- references/selector-strategy.md: セレクタ戦略

### テストケースの抽出

選択された各画面に対して、以下のテストケースを設計：

| 分類 | 内容 |
|------|------|
| **正常系** | 基本フロー、代替フロー、オプショナルフロー |
| **異常系** | バリデーションエラー、認証エラー、サーバーエラー |
| **境界値** | 空入力、最大長、特殊文字 |

### 優先度の設定

| 優先度 | 条件 | 例 |
|--------|------|-----|
| 高 | クリティカルパス、主要機能の正常系 | ログイン成功 |
| 中 | エラーハンドリング、準主要機能 | バリデーションエラー |
| 低 | エッジケース、UI詳細確認 | 特殊文字入力 |

### テストケース確認

```javascript
AskUserQuestion({
  questions: [{
    question: "テストケースを設計しました：\n\n- 正常系: X件\n- 異常系: Y件\n- 境界値: Z件\n\nこの構成で進めてよろしいですか？",
    header: "テストケース確認",
    options: [
      { label: "承認", description: "このテストケースで生成" },
      { label: "高優先度のみ", description: "優先度「高」のみ生成" },
      { label: "却下", description: "コマンドを終了" }
    ],
    multiSelect: false
  }]
})
```

## [4/6] テスト仕様書生成

### 出力先

```
tests/e2e/specs/{category}/{screen}.spec.md
```

- category: 画面の分類（auth, dashboard 等）
- screen: 画面名（kebab-case）

### テスト仕様書フォーマット

**Skill('playwright-guidelines')** のテスト仕様書フォーマット（SKILL.md 83-108行）に従って作成：

- 画面概要（画面ID、画面名、URL、認証）
- 前提条件
- テストケーステーブル（テストID、テスト名、前提条件、操作手順、期待結果、優先度）
- データ要件（テストデータ、Laravelファクトリー）
- Page Object要件
- **トレーサビリティマトリクス（必須）**

**テストID命名規則**: `{CATEGORY}_{SCREEN}_{連番}` または `{CATEGORY}_{SCREEN}_{種別}_{連番}`

### トレーサビリティマトリクス（必須）

テスト仕様書には**必ず**以下のトレーサビリティマトリクスを含めること。

```markdown
## トレーサビリティマトリクス

| 画面要素ID | 要素名 | 機能種別 | テストケース | カバレッジ状況 |
|-----------|--------|---------|-------------|--------------|
| ELM-001 | メールアドレス入力欄 | 入力 | AUTH_LOGIN_001, AUTH_LOGIN_ERR_001 | 正常系✓ 異常系✓ 境界値✓ |
| ELM-002 | パスワード入力欄 | 入力 | AUTH_LOGIN_001, AUTH_LOGIN_ERR_002 | 正常系✓ 異常系✓ 境界値✓ |
| ELM-003 | ログインボタン | ナビゲーション | AUTH_LOGIN_001 | 正常系✓ 異常系- 境界値- |
| ELM-004 | エラーメッセージ表示エリア | 表示 | AUTH_LOGIN_ERR_001 | 正常系✓ 異常系✓ 境界値- |
```

#### 機能種別の分類

| 機能種別 | 説明 | 例 |
|---------|------|-----|
| **入力** | ユーザーがデータを入力する要素 | テキストボックス、セレクトボックス、チェックボックス |
| **表示** | 情報を表示する要素 | ラベル、メッセージ、テーブル |
| **ナビゲーション** | 画面遷移を行う要素 | ボタン、リンク |

#### 未テスト検出ルール

機能種別ごとに**必須のテストカバレッジ**を定義し、未テスト要素を検出する：

| 機能種別 | 必須テスト | 検出条件 |
|---------|----------|---------|
| **入力** | 正常系✓ 異常系✓ 境界値✓ | 3種すべてがカバーされていない場合、警告 |
| **表示** | 正常系✓、条件分岐がある場合は異常系✓ | 正常系が欠けている、または条件分岐表示で異常系が欠けている場合、警告 |
| **ナビゲーション** | 遷移先確認テスト✓ | 遷移後のURL/画面確認テストが欠けている場合、警告 |

**検出された未テスト要素は [5/6] 品質チェックで報告し、修正を促す。**

## [5/6] 品質チェック

### テストケース網羅性の検証

生成したテスト仕様書が品質基準を満たしているか検証する。

#### チェック項目と修正指示

| # | 項目 | 確認内容 | 不合格時の修正指示 |
|---|------|---------|------------------|
| 1 | **正常系カバレッジ** | 主要機能すべてに正常系テストが存在する | 「{機能名}の正常系テストを追加してください」 |
| 2 | **異常系カバレッジ** | フォーム入力がある場合、バリデーションエラーテストが存在する | 「{要素名}のバリデーションエラーテストを追加してください」 |
| 3 | **境界値カバレッジ** | 数値入力・文字列入力がある場合、境界値テストが存在する | 「{要素名}の境界値テストを追加してください。例: 空文字、最大長」 |
| 4 | **前提条件の具体性** | 認証状態、データ状態が明確に記述されている | 「前提条件を具体化してください。例: 『ログイン済み』→『email: test@example.com でログイン済み、ダッシュボード画面を表示』」 |
| 5 | **操作手順の再現性** | 第三者が手順を見て再現可能な粒度で記述されている | 「操作手順を具体化してください。例: 『入力する』→『1. メールアドレス欄に test@example.com を入力 2. パスワード欄に password123 を入力』」 |
| 6 | **期待結果の検証可能性** | 「〇〇が表示される」等、具体的に検証可能な記述になっている | 「期待結果を検証可能な形式にしてください。例: 『成功する』→『"ログインしました"のトーストが画面右上に表示される』」 |
| 7 | **トレーサビリティ完全性** | 全画面要素がテストケースに紐付けられている | 「以下の要素にテストが不足しています: {要素リスト}」 |

#### 品質スコア計算

各チェック項目を0-100%で評価し、総合スコアを算出：

```
品質スコア = (合格項目数 / 7) × 100
```

| スコア | 判定 | アクション |
|--------|------|----------|
| 100% | ✅ 合格 | 次のステップへ進む |
| 70-99% | ⚠️ 条件付き合格 | 警告を表示し、修正を推奨 |
| 0-69% | ❌ 不合格 | 修正必須、再チェックが必要 |

### 品質確認ダイアログ

```javascript
AskUserQuestion({
  questions: [{
    question: "テスト仕様書の品質チェックを行いました：\n\n【トレーサビリティ確認】\n- 総要素数: X件\n- テスト紐付け済み: Y件\n- 未テスト要素: Z件\n  {未テスト要素がある場合はリスト表示}\n\n【カバレッジ確認】\n- 正常系: X件（主要機能: Y件中Y件カバー）✓/✗\n- 異常系: Z件（フォーム検証: あり/なし）✓/✗\n- 境界値: W件 ✓/✗\n\n【具体性確認】\n- 前提条件: 具体的✓/要改善✗\n- 操作手順: 具体的✓/要改善✗\n- 期待結果: 具体的✓/要改善✗\n\n【品質スコア】: XX% (合格/条件付き合格/不合格)\n\nこの品質で進めてよろしいですか？",
    header: "品質チェック",
    options: [
      { label: "承認", description: "この品質で次のステップへ進む" },
      { label: "修正", description: "指摘箇所を修正してから進む" },
      { label: "却下", description: "コマンドを終了" }
    ],
    multiSelect: false
  }]
})
```

**「修正」選択時**:
不合格項目ごとに上記「修正指示」に従った具体的な改善提案を表示し、テスト仕様書を修正後、再度品質チェックを実施する。

#### 修正指示の出力例

```markdown
## 品質チェック結果: 不合格（スコア: 57%）

### 修正が必要な項目

#### 1. 異常系カバレッジ ✗
**問題**: パスワード入力欄のバリデーションエラーテストが不足
**修正指示**: 「パスワード入力欄のバリデーションエラーテストを追加してください」
**追加すべきテストケース例**:
- パスワード未入力でのエラー表示
- パスワード文字数不足でのエラー表示

#### 2. 前提条件の具体性 ✗
**問題**: 「ログイン済み」という曖昧な記述
**修正指示**: 「前提条件を具体化してください」
**修正例**:
- Before: 「ログイン済み」
- After: 「email: test@example.com, password: password123 でログイン済み、ダッシュボード画面 (/dashboard) を表示」

#### 3. トレーサビリティ完全性 ✗
**問題**: 以下の要素にテストが紐付けられていない
**未テスト要素**:
- ELM-005: パスワードリセットリンク（ナビゲーション）
- ELM-006: 新規登録リンク（ナビゲーション）
```

## 重要な注意事項

### テスト仕様書作成のルール

1. **テストIDは一意に**: `{CATEGORY}_{SCREEN}_{連番}` 形式
2. **操作手順は具体的に**: 再現可能な手順を記述
3. **期待結果は検証可能に**: 「"ログイン成功"メッセージが表示される」のように具体的に
4. **前提条件は明確に**: 認証状態、データ状態を明示

### playwright-guidelinesとの連携

- **セレクタ戦略**: ロールベースロケーターを想定
- **AAAパターン**: Arrange-Act-Assert の構造を意識
- **テスト独立性**: 各テストケースが独立して実行可能
